================================================================================
 HOME CMMS — GETTING STARTED
================================================================================

A self-hosted Flask CMMS for home maintenance: Locations, Assets, Work Orders
(planned & unplanned), Job Plans, and Preventive Maintenance (PM) schedules that
auto-generate work orders on a fixed-day interval.

The database is SQLite — a single file, no database server to install or run.

This guide takes you from a fresh clone to a running, testable app.


--------------------------------------------------------------------------------
 0. PREREQUISITES

  Running this in Docker instead? See DOCKER.md — it covers compose, the
  environment variables, what lives in each volume, and backup and restore.

--------------------------------------------------------------------------------

  - Python 3.11 or newer

  That is the whole list. SQLite ships with Python, so there is no database
  server to install, start, or configure.


--------------------------------------------------------------------------------
 1. ACTIVATE THE VIRTUALENV & INSTALL DEPENDENCIES
--------------------------------------------------------------------------------

      source .venv/bin/activate
      pip install -r requirements.txt

  If .venv does not exist or is broken, recreate it. A venv breaks if the
  Python it was built against is removed or upgraded — the symptom is:

      bad interpreter: No such file or directory

  It holds nothing you cannot rebuild from requirements.txt:

      python -m venv .venv
      source .venv/bin/activate
      pip install -r requirements.txt


--------------------------------------------------------------------------------
 2. CONFIGURE ENVIRONMENT VARIABLES (OPTIONAL)
--------------------------------------------------------------------------------

  Every setting has a working default for local development, so you can skip
  this step entirely on a first run. To customise:

      cp .env.example .env

  For a Docker deployment copy .env.docker.example instead — it carries the
  container-only settings (WEB_PORT, TZ) and omits the paths below, which the
  image sets for itself.

  The settings that matter:

      FLASK_ENV=development
      SECRET_KEY=<a long random string>
      DATABASE_URL=sqlite:///instance/home_cmms.db   (default)
      UPLOAD_FOLDER=<absolute path>                  (defaults to ./uploads)

  SECRET_KEY is optional: leave it unset and one is generated on first run and
  stored in instance/secret_key. Set it explicitly if you would rather manage it
  yourself, or if instance/ is not persistent:

      python -c "import secrets; print(secrets.token_hex(32))"

  There is no built-in default key — a shared one would let anyone who read the
  source sign in as you. Sessions are signed with it, so changing it logs
  everybody out once.

  SIGN-IN PROTECTION
  Five failed sign-ins for an account, or twenty from one address, blocks
  further attempts for 15 minutes. If you lock yourself out, either wait or use
  Admin > Maintenance > Sign-in Attempts > Clear lockouts. Failed attempts are
  listed there too.

  DEBUG MODE
  FLASK_DEBUG=1 only works with HOST=127.0.0.1. The debugger runs arbitrary
  code for anyone who can reach the port, so the app refuses to start if you
  combine it with a network-facing HOST.

  Relative sqlite:/// paths resolve against the project root, so the CLI and
  the app always open the same file no matter where you launch them from.


--------------------------------------------------------------------------------
 3. CREATE THE DATABASE TABLES (MIGRATIONS)
--------------------------------------------------------------------------------

  The Flask CLI finds the app automatically via .flaskenv (FLASK_APP=run.py).
  The migrations/ folder is checked in, so all you need is:

      flask db upgrade

  That creates instance/home_cmms.db with all 8 tables: users, locations,
  assets, job_plans, job_plan_tasks, work_orders, pms, attachments.

  NOTE: Any time you change a model in app/models/, run:
      flask db migrate -m "describe your change"
      flask db upgrade

  Migrations run in Alembic "batch mode" because SQLite cannot ALTER most
  things in place — it rebuilds the table instead. This is already configured;
  you do not have to do anything for it.


--------------------------------------------------------------------------------
 4. CREATE THE FIRST ADMIN USER
--------------------------------------------------------------------------------

  Either start the app and open it in a browser — with no users yet you are
  taken to a setup page that creates the first administrator — or do it from the
  command line:

      python create_admin.py

  It prompts for username, email, and password (min 8 characters, entered
  twice, not echoed to the screen).

  The setup page is open to anyone who can reach the app until an account
  exists, so complete it before putting the app on an untrusted network. Set
  SETUP_WINDOW_MINUTES to close it automatically a few minutes after startup. This account has the 'admin' role and can
  manage other users. Safe to re-run — it refuses duplicate usernames/emails.


--------------------------------------------------------------------------------
 5. RUN THE APPLICATION
--------------------------------------------------------------------------------

      flask run

  Open http://127.0.0.1:5000 and log in with the admin account you created.

  The interface adapts to phones and tablets: the sidebar becomes a menu behind
  the button at the top left, and the wider tables drop their less important
  columns so rows fit without sideways scrolling. Every field is still on the
  record's own page.

  To make it reachable from other devices on your LAN (phone, tablet):

      flask run --host=0.0.0.0

  Then browse to http://<your-computer-ip>:5000 from another device.


--------------------------------------------------------------------------------
 6. RUN THE TESTS
--------------------------------------------------------------------------------

      pytest

  48 tests covering auth and access control, CSRF, input validation, PM
  schedule maths, the hourly scheduler, attachment cleanup, work order
  numbering and status lifecycle, and that every page renders.

  Tests build their own throwaway SQLite database in a temp directory and
  never touch instance/home_cmms.db.


--------------------------------------------------------------------------------
 7. TEST THE APPLICATION BY HAND (suggested walkthrough)
--------------------------------------------------------------------------------

  Work through the features in this order — each builds on the last:

  a) LOG IN
     - Go to /auth/login, sign in with your admin account.
     - You land on the Dashboard with summary stat cards.

  b) CREATE A LOCATION
     - Sidebar > Locations > "+ New Location"
     - e.g. name "Garage", add notes. Save.

  c) CREATE AN ASSET
     - Sidebar > Assets > "+ New Asset"
     - e.g. "Water Heater", category Plumbing, assign it to the Garage,
       fill in make/model/serial/install date. Save.
     - Open the asset detail page; try uploading a file (a PDF manual or
       a photo) under Attachments, then download and delete it.

  d) CREATE A JOB PLAN
     - Sidebar > Job Plans > "+ New Job Plan"
     - e.g. "Flush Water Heater". Click "+ Add Task" a few times and enter
       steps like "Turn off power", "Drain tank", "Refill". Save.
     - The tasks appear numbered on the job plan detail page.

  e) CREATE AN UNPLANNED WORK ORDER
     - Sidebar > Work Orders > "+ New Work Order"
     - Type "unplanned", link it to the Water Heater asset, set a priority
       and a due date in the past to see the red "overdue" highlight. Save.
     - Edit it, set status to "completed" — note the completed timestamp.
       Reopen it; the timestamp is kept as a record of when it was finished.

  f) CREATE A PM SCHEDULE (the core automation)
     - Sidebar > Preventive Maintenance > "+ New PM"
     - Name "Annual Heater Flush", link the asset + the job plan,
       interval 365 days, set "Next Due Date" to TODAY. Save.
     - On the PM detail page, click "Generate WO Now" to immediately create
       a planned work order. Confirm:
         * a new planned Work Order appears under "Generated Work Orders"
         * the PM's "Next Due Date" advanced by the interval
         * "Last Generated" is now today
     - The same generation happens automatically: a background scheduler
       checks every hour and creates planned work orders for any active PM
       whose Next Due Date has arrived. (See section 9.)

  g) ADMIN: ADD A SECOND USER
     - Sidebar > Admin > Users > "+ New User"
     - Create a standard "user" role account. Log out, log back in as them,
       and confirm the Admin menu is hidden for non-admins.

  h) REMEMBER ME
     - Ticking it on the login page keeps you signed in for 30 days, even
       after closing the browser. Leaving it unticked signs you out after 8
       hours of inactivity, or when the browser closes.
     - Both cookies are marked Secure only when FLASK_ENV=production, because
       a Secure cookie is never sent over plain http — forcing it on would
       stop you logging in over your LAN.

  i) CHANGE PASSWORD
     - Top-right > "Change Password" — verify the current-password check.


--------------------------------------------------------------------------------
 7b. MAINTENANCE (ADMIN)
--------------------------------------------------------------------------------

  Sidebar > Admin > Maintenance, for admins only. It covers:

  SYSTEM       Database, attachment and thumbnail sizes, free disk, record
               counts, versions, and whether image previews are working.

  PM SCHEDULER Whether the hourly check is running and when it next fires,
               plus a "Run check now" button. Useful because the timer
               restarts with the application, so a PM that has just come due
               may otherwise wait for the next tick.

  BACKUPS      "Create backup" writes one archive holding the database and
               every uploaded file, safely while the app runs. Download it
               somewhere else — a backup sitting beside the original is not a
               backup. "Keep" prunes to that many most recent archives.

  RESTORE      Replaces the database and every uploaded file from a backup,
               either one already in instance/backups or one you upload. It
               checks the archive before touching anything, saves the current
               state as pre-restore-<timestamp>.tar.gz first so a mistake can
               be undone, applies any pending migrations, and signs everyone
               out. Those pre-restore copies are never pruned by "Keep".

               A brand-new instance can also restore from the first-run setup
               screen, under "Restore from a backup instead" — that is how you
               move an existing instance to another machine.

  STORAGE      "Run scan" compares the attachment records against the files on
  INTEGRITY    disk and reports anything that has drifted apart. Cleanup is a
               separate button and tells you exactly what it will delete.

  DATABASE     Integrity check, reclaim space, fold in the write-ahead log,
               and clear the thumbnail cache.


--------------------------------------------------------------------------------
 7c. REST API
--------------------------------------------------------------------------------

  Other tools (Home Assistant, scripts, shortcuts) can raise work orders.

  GET A TOKEN
      Admin > Users > pick a user, then name the token after whatever will use
      it ("Home Assistant", "Phone shortcut") and press Generate.

      The token appears in its own box with a Copy button. It is shown once and
      cannot be recovered — but you can issue as many as you like. Give each
      integration its own, so revoking one does not break the others. The list
      shows when each was last used.

  LIVE REFERENCE
      Sidebar > API, or /api/v1/docs — every endpoint with its fields, a
      runnable curl example you can copy, and sample responses. It is rendered
      by the application, so it needs no internet connection and never goes out
      of date.

      These two pages are readable WITHOUT signing in, so you can point a tool
      at the spec directly. They describe the shape of the API only — no data
      from your instance appears in them, and every endpoint they document
      still requires a token. If you expose this app to the internet and would
      rather not publish the API surface, add @login_required back to the two
      view functions in app/api/routes.py.

      /api/v1/openapi.json is the same thing as an OpenAPI 3.1 document, if you
      would rather point Swagger UI, Postman or Insomnia at it.

  ENDPOINTS (all need the token)
      POST /api/v1/work-orders            create a work order
      GET  /api/v1/work-orders            recent ones, ?status= and ?limit=
      GET  /api/v1/work-orders/<WO-number>
      GET  /api/v1/assets                 asset numbers, parents and paths
      GET  /api/v1/locations              location numbers, parents and paths

  Assets and locations are referenced by NUMBER (AST-00001, LOC-00003), not by
  name — names are not unique.

  EXAMPLE
      curl -X POST http://localhost:5000/api/v1/work-orders \
        -H "Authorization: Bearer YOUR_TOKEN" \
        -H "Content-Type: application/json" \
        -d '{"title": "Furnace making a noise",
             "asset_number": "AST-00001",
             "priority": "high",
             "due_date": "2026-12-01"}'

  Leave out location_number and it is taken from the asset.

  ERRORS
      Every failure returns JSON with an "error" message, and validation
      failures add an "errors" object naming each bad field:

      {"error": "The work order could not be created.",
       "errors": {"asset_number": "No asset exists with number 'AST-99999'."}}

      400 invalid data   401 missing/bad token   404 no such record


--------------------------------------------------------------------------------
 7d. TIMES AND TIMEZONES
--------------------------------------------------------------------------------

  Times are shown in the timezone of the machine running the application, so
  they should match your own clock. Admin > Maintenance shows which timezone is
  in use, so you can check at a glance.

  Behind the scenes timestamps are stored in UTC and converted when displayed.
  That keeps them unambiguous when the clocks change — during a daylight-saving
  fallback the same local hour happens twice, which would otherwise make the
  order of events impossible to work out.

  Nothing needs configuring on a normal install; the system timezone is used.
  In a container, set TZ:

      docker run -e TZ=America/New_York ...

  No internet connection is needed for any of this.


--------------------------------------------------------------------------------
 8. WHERE YOUR DATA LIVES
--------------------------------------------------------------------------------

      instance/home_cmms.db     the entire database, one file
      uploads/<type>/<id>/      attachment files, by entity

  Both are gitignored.

  TO BACK UP, do NOT just copy the .db file. SQLite runs in WAL mode, so recent
  writes live in home_cmms.db-wal and a plain copy silently gives you a stale
  snapshot. Use SQLite's own snapshot instead, which is safe while the app runs:

      sqlite3 instance/home_cmms.db "VACUUM INTO 'backup.db'"

  or from Python:

      python -c "import sqlite3; sqlite3.connect('instance/home_cmms.db')\
                 .execute('VACUUM INTO ?', ('backup.db',))"

  Then copy uploads/ alongside it.


--------------------------------------------------------------------------------
 8b. LOCATIONS, ASSETS, STATUS AND DELETION
--------------------------------------------------------------------------------

  HIERARCHY
  Locations and Assets both nest. A location can sit inside another
  ("Coleman House > Basement > Utility Room"), and an asset can be a
  sub-assembly of another ("HVAC System > Blower Motor"). Set the parent on the
  edit form; list pages show the tree indented. A record can never be placed
  beneath one of its own children — the form rejects that with an explanation.

  NAMES AND NUMBERS
  Every asset gets a permanent number (AST-00001, AST-00002, ...) shown in
  lists, on the detail page and in every picker. Asset names do NOT have to be
  unique — two "Router" entries are fine, and the number plus the location tells
  them apart when you are choosing one.

  Location names must be unique among locations sharing the same parent, and the
  check ignores capitalisation. So "Basement > Bathroom" and "Main Floor >
  Bathroom" can both exist, but two "Bathroom"s directly under Basement cannot,
  and neither can two top-level locations with the same name.

  STATUS
  Every location and asset has one of three statuses:

      Active           In service. The only status offered when picking an
                       asset or location for a new work order or PM.
      Inactive         Temporarily out of service. Existing work is untouched,
                       but it cannot be chosen for new work.
      Decommissioned   Retired for good. Kept for history; not selectable.

  Editing an existing work order that already points at an Inactive or
  Decommissioned record keeps that link in the dropdown, so saving the form
  never silently clears it.

  DELETION
  Following Maximo: anything with work recorded against it is never deleted,
  because that would orphan the history. A location or asset can only be
  deleted while nothing references it — no child records, no assets in it, no
  work orders, no PM schedules. When something does reference it, the detail
  page replaces the Delete button with an explanation of exactly what is in the
  way and a link to change its status instead.

  So the normal way to retire something is to set it Decommissioned, not to
  delete it.

  SEEING LONG FIELD CONTENTS
  Hovering over any text box shows its full contents as a tooltip, which helps
  when a value is longer than the box. Password fields are excluded.

  FINDING THINGS IN LONG DROPDOWNS
  Asset, location, parent and job plan pickers filter as you type. Typing
  matches anywhere in the entry, not just the start, so "nas" finds
  "Synology NAS" and "kitchen" finds every asset in the Kitchen. Arrow keys
  move, Enter picks, Escape cancels.

  COMPLETED DATE
  Work orders have a Completed Date you can set by hand — useful when logging
  work after the fact. Leave it blank and set the status to Completed and it
  fills in with today's date. Clearing it on a work order that is not completed
  removes it.

  JOB PLANS
  A job plan holds three lists: the tasks to perform, the materials required and
  the tools required. Materials can carry a quantity ("2 rolls"). The plan's
  total duration is the sum of the task estimates, shown on the detail page and
  in the Duration column of the list.

  Tasks, materials and tools can be reordered by dragging the handle at the left
  of each row, or with the up/down arrows next to it. Saving writes the sequence
  in the order shown, so dropping a new task into the middle works as expected.

  Job plan attachments are added on the create and edit screens rather than the
  detail page.

  MATERIALS AND TOOLS ON WORK ORDERS
  A work order has its own materials and tools lists. Attach a job plan and its
  lists are copied across when you save; you can then edit them freely, because
  what a job actually used often differs from what the plan called for. A work
  order with no job plan can carry lists of its own.

  Materials take a part number as well as a description and quantity.

  MATERIALS USED, ON THE ASSET
  You can add part numbers you already know directly on the asset page — no
  work order needed. Adding one that is already listed updates it rather than
  creating a duplicate, and a later work order using the same part starts
  counting against the entry you made.

  When a work order against an asset is COMPLETED, its materials are added to
  that asset's "Materials Used" list — so next time you need the part, open the
  asset and the number is there. Using the same part again updates the existing
  entry with a new date and a count, rather than adding a duplicate. The entry
  survives the work order being deleted.

  Tools are not rolled up; only consumables.

  ASSET PHOTOS
  An asset can carry one optional photo, shown as a card on its detail page
  (and nowhere else). Add or replace it under Photo; replacing deletes the
  previous image. PNG, JPG, GIF and WEBP are accepted. Click the photo to open
  it full size.

  IMAGE PREVIEWS
  Photos and other images show a small thumbnail next to their name. Click it
  to view the picture full size over the page — no download, press Escape or
  click outside to dismiss. Other file types show a chip with their extension
  instead. Use the filename link to download the original.

  ATTACHING SEVERAL FILES
  Every file picker takes more than one file at a time — select a batch and
  upload them in one go. The friendly name only applies when you pick a single
  file; a batch keeps each file's own name, and you can rename them afterwards.

  ATTACHMENT NAMES
  Every attachment can carry an optional friendly name — "Furnace manual"
  instead of MAN-4471-rev-c.pdf. Set it when uploading, or use Rename on any
  file afterwards. The real filename stays visible next to it, and downloads
  save under the friendly name with the original extension kept.

  DOCUMENTS ON WORK ORDERS
  All five record types take file attachments. A work order additionally shows a
  "Related Documents" section pulling in files held on its PM, job plan, asset
  (and any parent assets), and its location chain. These are links to the
  originals, not copies — update the manual on the asset and every work order
  showing it picks up the new version. A work order created from a PM therefore
  arrives with the PM checklist and job plan paperwork already attached.

 9. HOW THE PM SCHEDULER WORKS
--------------------------------------------------------------------------------

  - A background scheduler (APScheduler) starts inside the Flask process and
    runs once per hour.
  - It finds every ACTIVE PM whose next_due_date is today or earlier and that
    has not already generated a work order today, then:
        * creates a PLANNED work order (carrying over the asset, location,
          and job plan), and
        * advances the PM: last_generated_date = today, and next_due_date
          moves forward by one interval FROM THE PREVIOUS DUE DATE.
  - "Work Order Priority" is the priority given to the work orders this PM
    generates. Defaults to Medium.

  - "Generate Ahead (days)" creates the work order early, so there is time to
    order parts or book a slot. A PM due on the 30th with 14 days' lead starts
    generating on the 16th; the work order still shows the 30th as its due
    date. This must be less than the interval, or the PM would generate every
    day.

  - "Overdue Grace (days)" is how long past the due date something can sit
    before it is flagged overdue in red. It exists on both PMs and work orders,
    and a work order generated from a PM inherits the PM's setting. A work
    order due on the 1st with 5 days' grace is not overdue until the 7th.

  - Each PM chooses how its next due date is worked out, via the "Schedule Based
    on Last Completed" checkbox:
        * OFF (default) — fixed rhythm. The next due date is one interval after
          the previous DUE date, so an annual job stays on its anniversary even
          if you finish it a fortnight late.
        * ON — floating. The next due date is one interval after the work was
          actually COMPLETED, so finishing late pushes the whole cycle out.
          Good for things measured from actual service, like an oil change.
    With a 30-day PM due on the 1st and completed on the 10th, fixed comes due
    on the 31st; floating comes due on the 40th day. Where several work orders
    exist for the PM, the most recent completion is the one that counts.

  - Anchoring to the due date rather than to "today" is deliberate: a late
    scheduler tick or a manual "Generate WO Now" therefore does not shift the
    anniversary of every future occurrence. If a PM is several intervals
    overdue (the app was off for a while), whole intervals are skipped so you
    get one catch-up work order, not a backlog of them.
  - The work order and the schedule advance commit as ONE transaction, so a
    crash between them cannot produce a duplicate on the next tick.
  - Because it only runs hourly, a newly-due PM may take up to an hour to fire
    on its own. Use "Generate WO Now" on the PM page to trigger it instantly.
  - A PM that fails to generate is logged and skipped; the others in that pass
    still go through.
  - The scheduler only runs while the app is running. Set SCHEDULER_ENABLED=0
    to turn it off (create_admin.py and the tests do this automatically).

--------------------------------------------------------------------------------
 11. TROUBLESHOOTING
--------------------------------------------------------------------------------

  "Database not initialised" page
      - The schema does not exist yet — usually a new install, or you cleared
        the instance folder. Run:  flask db upgrade
        Then reload; you will be offered the first-run setup page. In Docker
        this happens automatically, so just restart the container.

  "Target database is not up to date" / table already exists
      - You changed models without migrating. Run:
            flask db migrate -m "change"  &&  flask db upgrade

  "database is locked"
      - Two processes are writing at once. The app sets a 30-second busy
        timeout and WAL mode, so this should be rare; it usually means a
        second copy of the app is running. Stop the extra one.

  "SECRET_KEY must be set when FLASK_ENV=production"
      - Working as intended. Put a real SECRET_KEY in .env.

  flask: command not found
      - The virtualenv isn't active. Run:  source .venv/bin/activate

  Uploaded files don't save
      - UPLOAD_FOLDER must be a path the app can write to. It is created on
        startup, but the parent directory must exist and be writable.

  Changes to .env not taking effect
      - Restart the app. Environment is read at startup.


--------------------------------------------------------------------------------
 12. PRODUCTION / EXPOSING TO THE INTERNET (later)
--------------------------------------------------------------------------------

  The auth layer (Flask-Login sessions, hashed passwords, CSRF tokens, secure
  cookie flags, same-origin-only login redirects) is built to be
  internet-ready, but before exposing it:

  - Set FLASK_ENV=production in .env. This flips SESSION_COOKIE_SECURE on, so
    cookies are only sent over HTTPS, and makes SECRET_KEY mandatory.
  - Do NOT use `flask run` in production. Use a WSGI server, e.g.:
        pip install gunicorn
        gunicorn -w 1 "run:app"
    Use ONE worker. SQLite allows a single writer, and each extra worker would
    start its own PM scheduler and generate duplicate work orders. For a
    household-sized instance one worker is plenty. If you ever outgrow it, run
    the app with SCHEDULER_ENABLED=0 across several workers and run one
    dedicated scheduler process alongside them.
  - Put it behind a reverse proxy (nginx / Caddy) terminating TLS.
  - Use a strong, unique SECRET_KEY.
  - There is no login rate limiting; if you expose this publicly, add it at the
    proxy (nginx limit_req, Caddy rate_limit) or with Flask-Limiter.
  - Every signed-in user can view and edit every record. The 'admin' role only
    gates user management. Only give accounts to people you trust with all of
    the data.
